## 3. 資料生成

CSV 固定五欄：`timestamp`、`temp`、`pressure`、`vibration`、`label`。共 500 筆，每分鐘一筆，時間為 2026-11-07 12:00:00–20:19:00（台北時間）。

| 感測器 | 正常範圍   | 嚴格異常       | 小數位 |
| ------ | ---------- | -------------- | -----: |
| 溫度   | 45–50°C  | <43 或 >52     |      1 |
| 壓力   | 1.00–1.05 | <0.97 或 >1.08 |      2 |
| 振動   | 0.02–0.04 | >0.07          |      2 |

正常範圍外、未嚴格超標為灰區；等於嚴格邊界不算超標。壓力與振動不另加未指定單位。

### 3.1 基線分布

以下為事件注入與量化前的生成分布；最終 CSV 混入事件、四捨五入及缺值後，不再是單一連續分布。

| 變數      | 分布與參數                                     | 平均值／標準差    |
| --------- | ---------------------------------------------- | ----------------- |
| temp      | 常態：μ=47.5、σ=0.7                          | 47.5／0.7         |
| pressure  | 常態：μ=1.025、σ=0.007                       | 1.025／0.007      |
| vibration | Gamma：shape=36、scale=0.03/36 ≈ 0.0008333333 | 0.03／0.005，恆正 |

seed 42 分出基線、事件、label、隨機缺值四個亂數流程，固定參數即可重現。

### 3.2 時間與變數關係

每分鐘抽取三維相關常態擾動 `ε_t`，再建立 AR(1) 潛在序列 `z_t`。矩陣順序為溫度 T、壓力 P、振動 V：

```text
Σ = [[1.00, 0.55, 0.75],
     [0.55, 1.00, 0.65],
     [0.75, 0.65, 1.00]]
ε_t ~ Normal(0, Σ)，各分鐘獨立抽樣
z_0 = ε_0
z_t = 0.8 × z_(t-1) + 0.6 × ε_t

temp_t      = 47.5 + 0.7 × z_(t-2,T)
pressure_t  = 1.025 + 0.007 × z_(t,P)
u_t         = clip(Φ(z_(t,V)), 10^-12, 1-10^-12)
vibration_t = GammaPPF(u_t, shape=36, scale=0.03/36)
```

- 第一筆交付資料對應 `t=2`；溫度使用兩分鐘前的潛在狀態，模擬較慢的熱反應。壓力與振動使用當分鐘狀態。
- `Φ` 是標準常態累積分布，`GammaPPF` 將常態分位轉成 Gamma 分位；這是保留振動恆正邊際分布的 Gaussian copula 做法。
- 三者以相關擾動近似共同負載影響。`Σ` 是潛在同時相關，不是最終 CSV 相關；延遲、Gamma 轉換與量化都會改變觀測結果。
- 前 250 筆實測 lag-1 自相關：溫度 0.815、壓力 0.626、振動 0.652；同時相關：溫壓 0.272、溫振 0.370、壓振 0.520。

### 3.3 Label 與事件

- 量測先量化至指定精度，再生成 label，最後加入回傳問題。嚴格超標的 abnormal 機率為 100%；未超標時，灰區欄數 0／1／2／3 對應機率為 1%／10%／40%／80%。
- 已驗收資料有 62 筆 abnormal（12.4%）、12 格缺值（連續 4 格＋隨機 8 格）與一筆壓力 999。隨機缺值避開前 250 筆、指定事件及正常量測但 label abnormal 的展示案例。
- `data/generation_metadata.json` 僅供生成與離線驗收，不提供給偵測器或 Agent。label 模擬外部判斷，與感測器有條件關聯，不代表真實 AOI 獨立真值。

## 4. 異常判定與事件

流程：已讀回報 → 資料品質／有限補值 → 規則＋Isolation Forest＋AOI＋持續時間 → 風險、事件與工單。

- 初始化讀前 250 筆：前 200 筆訓練、後 50 筆校準；第 251 筆起逐筆監測。模型僅使用三個感測器，不以 label 篩選訓練資料。
- Isolation Forest 固定 100 棵樹、random_state=42。原始異常分數轉為校準資料的 0–100 百分位；越高越偏離基準，不是故障機率。
- 模型關注門檻為 98；連續三筆有效原始量測達 98 才形成模型警告。監測期間更新評分與計數，不重新訓練。

| 設備等級 | 觸發條件                                                                                   |
| -------- | ------------------------------------------------------------------------------------------ |
| 正常     | 三欄有效且無觸發條件，亦無待解除事件                                                       |
| 關注     | 有效量測進入灰區、未補值模型分數達 98，或 label abnormal                                   |
| 警告     | 任一有效量測嚴格超標；模型達 98 連續三筆；至少兩欄灰區連續三筆；或 label abnormal 連續三筆 |
| 危急     | 同筆至少兩欄嚴格超標，或同欄連續三筆嚴格超標                                               |
| 未知     | 觀測不足且無可用警報證據                                                                   |

- 缺值、999、非有限值列為資料品質問題。有效前值最多暫補兩分鐘；沒有前值或超期即不可用。999 當筆警告；短缺值先關注，無可用補值時警告。
- 補值不修改 CSV；暫補模型分數不單獨觸發設備警告或解除事件。連續相同值只記錄，不發卡值告警；目前欄位不足以確認卡值。
- 同段設備異常沿用同一事件並保留最高風險；當前類型、感測器與檢查方向隨新回報更新，峰值證據及歷史感測器關聯另存。品質問題獨立追蹤；相關觸發消失且連續三筆原始回報有效後解除。
- 警告／危急建立並更新同一份工單草稿。告警恢復與維修完成分開；根因為待查候選，不作確診或自動派工。

## 5. Ollama 與互動問答

使用本機 `qwen3:4b-instruct`，固定連線 `127.0.0.1:11434`，檢查本機權重與工具能力。允許 Ollama 雲端功能開啟，專案推論仍使用本機模型。

### 監測中自動解說

- 需處置事件新增或風險／類型／感測器改變時，在背景呼叫模型；AOI 關注也可觸發解說。等待期間先顯示規則建議，過期回覆捨棄。
- 三個唯讀工具：`get_event` 取事件證據、`get_history` 取當下最近 12 筆回報、`get_playbook` 取固定知識卡；不讀未來資料。工具歷史將非有限值轉為 null 並標示無效，保留原始 CSV，避免 JSON 紀錄中斷監測。
- 模型排序既有根因候選，生成「目前狀況、優先檢查理由、查核後處置」。程式保留知識卡第一步，後續分為現場確認異常／未確認異常兩條檢查方向。
- 建議驗證後同步終端、事件、工單與 HTML，並標示來源及依據時間。風險、優先程度與恢復由程式決定。
- 每次最多三輪模型請求、四次工具呼叫、30 秒；模型失敗或輸出不合格時保留規則建議，監測繼續。

### 監測後三項問答

| 工具                        | 功能                                                                   |
| --------------------------- | ---------------------------------------------------------------------- |
| `query_history`           | 依批次、事件／工單編號、關鍵字或時間查詢；單一事件提供預警與超標時間線 |
| `handoff_summary`         | 程式計算事件數、恢復數及待確認工單，模型整理交班重點                   |
| `propose_work_order_edit` | 查到唯一工單後建立修改預覽；只允許問題摘要、工單說明及現場備註         |

未指定批次時固定查最近一批；「本次／上一批」或明示批次 ID 由程式決定，模型不能另選，來源會顯示批次。只輸入修改編號時先詢問內容；輸入「儲存」才新增修訂，「取消」或離開不套用。模型沒有儲存權限。

歷史與交班回答由模型挑選、排序已查到的事實，程式直接帶入紀錄中的時間、數量及工單狀態。即時處置說明與工單草稿修改仍使用模型生成文字。

每題最多三輪模型請求、30 秒。回答須引用已查紀錄；格式異常限次重試，失敗時提示並保留資料。文字驗證不能取代現場查核。

## 6. 終端與結果保存

- 終端以固定欄寬顯示「感測器／原始回報／作業條件／回報狀態」，並列設備綜合評估、AOI 設備監測、資料品質與運轉觀察。
- 三圖呈現最近 60 筆原始回報與嚴格邊界；缺值、999 留斷點，不畫補值。小視窗使用精簡排版，完整建議保留於結果頁。
- 預設只顯示風險與處置重點，分數及工具細節留在技術紀錄；不顯示逐筆進度或模型思考過程。

| 本機產物                                                                  | 寫入方式                                         |
| ------------------------------------------------------------------------- | ------------------------------------------------ |
| `readings.jsonl`、`agent_trace.jsonl`                                 | 開始監測時重建，執行期間逐步寫入                 |
| `events.json`、`work_orders.json`、`summary.json`、`results.html` | 結束或 Ctrl+C 時保存；同目錄更新為本次結果       |
| `history.sqlite3`                                                       | 每次結束新增批次；人工修訂追加版本，保留原始快照 |
| `chat_trace.jsonl`                                                      | 問答期間追加工具與回覆紀錄                       |
| `history/<批次>/results.html`                                           | 人工確認修訂後產生對應歷史頁                     |

`results.html` 是機台負責人的離線閱讀入口。舊驗收資料與人工內容保留本機；GitHub 不提交 `outputs/`。備份與重現方式見 [README](../README.md#results)。

## 7. 操作指令

先安裝 `requirements.txt`，並啟動已下載指定模型的 Ollama；所有指令在專案根目錄執行。

```bash
.venv/bin/python main.py                         # 監測；互動終端正常結束後進入問答
.venv/bin/python main.py --chat                  # 直接查已保存紀錄
.venv/bin/python main.py --no-ollama --interval 0 # 純終端快速重播
.venv/bin/python evaluate_model.py               # 重建模型評估結果
.venv/bin/python -m unittest discover -s tests -q # 全套測試
```

`--interval` 控制每筆秒數，預設 0.5；`--output-dir` 可另存結果。`--no-ollama` 不進入模型問答。生成器仍可獨立執行，已驗收的 `data/` 維持不變。

## 10. 原始計劃想法

原始規劃先以 grill-me 釐清需求，再以 grilling 檢視盲點；專案拆為四部分：**模擬資料生成 → 異常判定與處置 → AI Agent 串接 → Demo 美化**。

與 Agent 確認後的原始執行順序為：需求問答與規劃 → 主種子資料 → 使用者驗收 → 純終端全流程 → 使用者驗收 → Ollama 與三項問答 → Demo 最終驗收 → 正式文件。每階段先交付可執行結果，再依使用者回饋修正；目前使用者已確認實作告一段落，授權文件先行，正式展示紀錄後補。

| 面向       | 原始／初期安排                         | 目前做法與優化目的                                                   |
| ---------- | -------------------------------------- | -------------------------------------------------------------------- |
| 資料生成   | 常態溫壓、Gamma 振動，具時間與物理關聯 | 明確固定分布參數、相關矩陣、兩分鐘延遲與回報精度，便於重現           |
| 模型判定   | 即時量化異常，結合門檻、AOI 與持續時間 | 固定訓練／校準、百分位與連續條件，加入離線評估並保留 9 分鐘提前預警  |
| 固定值     | 連續相同數值作為回傳失效線索           | 僅記錄；現有欄位無法區分穩態與卡值，避免誤報                         |
| 使用者解讀 | 顯示異常分數、風險與建議               | 主要畫面呈現作業條件及「與平常相近／不同」，分數留供查核             |
| 模型建議   | 初期模板為主，模型主要排序候選原因     | 加入情境、查核理由及兩條後續分流，讓模型產出具體可用的差異           |
| 地端條件   | 初版要求 Ollama 停用雲端功能           | 取消開關限制，保留指定本機模型與工具檢查，減少使用阻擋               |
| Agent 範圍 | 以即時監測、告警與維修建議為主         | 增加歷史、交班、草稿修改三項問答，維持簡單範圍                       |
| 問答可信度 | 驗證模型引用的紀錄 ID                   | 固定查詢批次，模型選擇事實、程式帶入關鍵內容，避免錯批或虛構狀態       |
| 結果保存   | 同目錄 JSON 更新為本次結果             | 加入中文 HTML、SQLite 批次與修訂版本，保留歷史及人工內容             |
| Demo       | 彩色終端與格式化表格                   | 固定欄寬、近期三圖、嚴格邊界、缺值斷點與小視窗排版                   |
| 專案維護   | Python 模組與驗收輸出逐步累積          | 集中 factory_agent 與 validation，保留入口及重現方式，方便操作與檢視 |
